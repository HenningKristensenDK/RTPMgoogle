## Risk scoring — Likelihood x Impact (Group G, 2026-07-22)
Risk `priority` (low/medium/high/critical) is no longer manually set anywhere in the app — it's ALWAYS derived from `riskScore = likelihood * impactScore` via non-linear bands in `src/lib/riskScoring.ts` (`priorityFromScore`): Low 1-4, Medium 5-9, High 10-16, Critical 17-25. New fields on every `risks` doc: `likelihood` (1-5, "Rare"→"Almost certain"), `impactScore` (1-5, "Negligible"→"Severe"), `impactDriver` (single-select enum: Cost/Schedule/Safety/Quality — the one dominant dimension, not a full matrix, by design), `riskScore`, `trend` (up/flat/down, manually cycled by the risk owner, defaults `"flat"`). Field name kept as `priority` for backward compat with every existing read-site — only how it gets SET changed. No inherent/residual split, no risk appetite thresholds — deliberately out of scope for this pass.
- **Creation** (`NewRiskModal.tsx`) and **detail edit** (`RiskMetadata.tsx`) both now show Likelihood/Impact/Impact-driver selectors instead of a manual Priority dropdown, with the derived result shown as a read-only colored pill ("Priority: Critical (score 20)"). `RiskStatusBar.tsx` gained a small up/flat/down trend control (top-right of the card, click to cycle) and the Risk Register table shows the same trend icon next to each row's Priority.
- **Dashboard Risk Matrix** rebuilt from a Workstream x Priority count table into a real 5x5 Likelihood (rows) x Impact (columns) grid — each cell's zone color comes from that cell's own score (not from real data), each open risk plots as a count badge in its (likelihood, impactScore) cell, clicking any cell filters the Risk Register by that cell's priority band (reuses the existing `presetPriority` nav-state pattern from `RiskBoard.tsx` — no new filter plumbing needed).
- Applies uniformly to both `kind: "risk"` and `kind: "opportunity"` docs (same collection/schema) — no separate opportunity-specific scoring model.
- **Backfill approach**: existing risks predate this and had no `likelihood`/`impactScore`. `backfillScoring()` in `lib/riskScoring.ts` maps each risk's existing manually-set `priority` to a likelihood/impact pair chosen so recomputing the score lands back in the SAME band (critical→4×5=20, high→4×3=12, medium→3×2=6, low→2×2=4) — nothing visually jumped priority band on migration. `impactDriver` backfilled via a simple keyword heuristic on title+notes (safety/hse→Safety, quality/ncr/defect→Quality, cost/budget/compensation→Cost, else→Schedule); `trend` defaults to `"flat"`. Same function now runs at fresh-seed time too (`src/lib/seed.ts` and `scripts/seed.ts`), so a brand-new project gets real scoring from day one, not just a backfill patch. Live migration was a surgical field-level patch (not a reseed, matching the `migrate-customer-name-and-eq-parent.ts` pattern): `scripts/migrate-risk-scoring.ts`, run 2026-07-22 against `rtpm--v2` — patched all 20 existing risk docs, 0 errors (one doc, `RK-011`, had already been renumbered `RK-021` by an earlier, unrelated Risk/Opportunity-kind-toggle test — not a migration bug). Backed up first to `backups/2026-07-22/` (gitignored, local only).

**Full v4 doctrine** (read directly from the local checkout's `CLAUDE.md` + `docs/marketing-rules.md`, since the npm-installed copy is missing both):
- **Tie-breaker**: RTPM should resemble a board presentation before a marketing campaign. Never expand the palette, add accent colors, increase visual complexity, or weaken the one-highlight rule.
- **Hierarchy: Position > Size > Colour > Weight** — solve communication with layout/scale/whitespace before reaching for color; color reinforces, it doesn't lead.
- **Colour meaning**: Indigo `#0D08D2` = insight/principle/conclusion (default emphasis on light grounds). Gold `#FFCC00` = breakthrough/takeaway/the one action (dark grounds only; on the website, CTA only — never a text highlight). Ink Navy `#070474` = dark surface only, never an accent.
- **One-highlight rule**: exactly one highlight per canvas/screen, gold on dark / indigo on light, never both. Applies to marketing assets; for this app (product UI) the equivalent is the one-primary-button rule below.
- **Never hardcode** a color, font, spacing, or radius — always a semantic token (`--color-*`, `--type-*`, `--radius-*`, `--font-*`) from `tokens/tokens.css`. If a needed value has no semantic token yet, flag it — don't invent a hex/pixel value.
- **Reuse components first**: `Button`, `Card`, `Kpi`, `StatusPill`, `StatusStepper`, `Logo` — real components, real props (`ButtonProps`, `CardProps`/`CardPadding`, `KpiProps`/`KpiOwner`/`KpiTrendDirection`/`KpiGoodDirection`, `StatusPillProps`/`StatusLevel = 'critical'|'high'|'medium'|'low'|'none'`, `StatusStepperProps`/`Step`/`StepState = 'done'|'current'|'pending'|'overdue'`, `LogoProps`/`LogoLockup`/`LogoColorway`), all exported from `index.ts`. **Blocked from actual import in this app right now by the packaging bug above** — until fixed, build local equivalents in `src/components/` matching these exact prop shapes (semantic tokens only) so swapping in the real package later is a drop-in, not a rewrite.
- **At most one `<Button variant="primary">` per screen** — gold means "the one thing to do here."
- **Status colors fixed-meaning, never repurposed**: critical=red, high=orange, medium=amber `#E0A800` (never gold), low/done=green, none=grey — this is `StatusPill`'s actual 5-value `StatusLevel` union, directly comparable to this app's own `priority` field (see conflict below).
- **Logo**: always via `<Logo />`, never hand-drawn divs/SVG; respect `docs/logo-spec.md` lockup rules (e.g. Lockup B needs ≥40px icon height).
- **Website/product typography: Inter only** (`--font-ui`). Montserrat is retired — never use it, including anywhere this file previously said to. Barlow Semi Condensed (`--font-display`) is marketing-only (LinkedIn/decks/thumbnails) — never in product/website UI.
- **Icons**: thirteen module pictograms only, sharp corners, monoline — never a library icon set (Lucide, Feather, etc.), never applied to a role/sector/page type.
- If a task needs a value/component/pattern that doesn't exist in the token/component set yet, **stop and flag it** rather than improvising a one-off.
